## 3. 実装と試験で見つけて直したこと

| 問題 | 対応 |
|---|---|
| 計画を作り直すと採番が進んで別の計画になり、同じ候補が二重に計画された | 反映待ちの計画に入っている候補は、新しい計画に入れない（キーと指紋で照合） |
| 要確認の印をすべて個別確認にすると、実際の記録で 6 件中 1 件しか「すべて選択」できなかった | 個別確認を必須にする印を、誤った確定につながる 5 つに絞った（計画書 0 章） |
| 反映した後もカードが「承認」のまま、自分自身が似た項目として出た | 反映済み・反映待ちを表示し、選択と計画から外す |
| 統合で戻した要点の言い換え重複（Phase D） | 許容して Phase D の報告書に記録 |

## 4. 残るリスク

- 重複照合の閾値（0.85・0.65）は仕様の初期値のまま。実際の管理項目が増えたら評価データで調整する
- 候補の project はセッションの project（未指定は「未分類」）
- 取り込んだ項目の project は、取込みのときに「管理」タブで選んでいるセッションの project になる。ファイルの中の project の列は読まない
- 取込みは実際の利用者のファイルで試していない（利用者に既存の管理ファイルが無い）。見本のファイルと自動テストの書式（チェックリスト・表）以外の書き方は、読めずに飛ばした行として報告する
