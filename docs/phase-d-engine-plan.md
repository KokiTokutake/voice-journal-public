# 推論エンジンの同梱（LM Studio への依存をやめる）計画

- 状態: **承認済み（2026-11-05）**。8 章の 3 点も合意: llama-server を同梱し移行期間は LM Studio も選べる、D5 の受入は置き換えた後に測る、更新の自動化と出力の抑制は後か並行
- 根拠: 2026-11-05 の利用者の判断「LM Studio 依存をやめる方向で改修を進めたい」。D5 の評価で分かった問題（下の 1 章）
- 関係する文書: 詳細仕様書（LM Studio を前提にした記述 22 か所）、環境構築仕様書・手順書（12 か所）、`CLAUDE.md`（3 か所）、`docs/environment-lock.md` 6 章、`docs/phase-d-plan.md`

## 1. 背景

D5 の評価で、LM Studio を通して使うことの問題がはっきりした。

| 問題 | 内容 |
|---|---|
| メモリが戻らない | llama-server が推論のたびに増え、待機しても減らない（25 分の会議 1 回で +1.6 GB）。TTL で解放されるまで常駐する |
| 設定がぶれる | 要求で自動的に読み込まれるときは、LM Studio のモデルごとの既定値を使う。利用者がモデルごとに設定しないと、文脈長が最大（128K）になりうる |
| 取得が不安定 | `lms get` が ggml-org のリポジトリで失敗した（MTP 用のファイルだけを選んだ） |
| 版が固定できない | LM Studio と実行環境（llama.cpp）の版は LM Studio が自動で上げる。評価の数字を比べにくい |
| 配布 | 利用者に LM Studio を別に入れてもらう必要がある（Phase G） |

## 2. 方針

**llama.cpp の `llama-server.exe` を、版を固定して同梱し、アプリが子プロセスとして起動する**。文字起こしの whisper.cpp（`whisper-cli.exe`）と同じやり方にする。

- `llama-server` は OpenAI 互換の API（`/v1/chat/completions`、`response_format: json_schema`）を持つので、今の LM Studio のクライアントの大部分を使える
- **記録を作るときだけ起動し、ジョブが終わったら（または一定時間使わなければ）終了する**。メモリは毎回戻る
- 起動の引数（文脈長・並列数・GPU・mmap・思考）はアプリが毎回同じ値で渡す。利用者の設定は要らない
- 待ち受けは `127.0.0.1` の空いているポートだけ。起動ごとに作るランダムな API キーを付け、ほかのプロセスから使えないようにする
- **移行期間は LM Studio も設定で選べるようにする**（既定は同梱のエンジン）。同梱のエンジンで問題がなければ、LM Studio の経路を外すかを別に決める

使わないもの: LLamaSharp（同じプロセスの中で動くのでメモリを確実に返しにくく、llama.cpp への追従が遅れがち）、ONNX Runtime GenAI（Gemma 4 への対応が不明。NPU は Phase H の任意の最適化）

## 3. 範囲

**含む**

- エンジン: llama.cpp の Windows Vulkan 版を版と SHA-256 で固定して取得する（`%LOCALAPPDATA%\VoiceJournal\tools\llama.cpp\`）。`environment-lock.md` に記録。ライセンス（MIT）の表示
- モデル: GGUF を `%LOCALAPPDATA%\VoiceJournal\models\llm\` に置き、SHA-256 で検査する。既定は Gemma 4 E2B Q4_0（ggml-org）。設定でモデルを選べる（E4B を高品質の選択肢にできる）
- 起動と終了（Infrastructure）: 起動の引数、空いているポートの選択、準備ができたかの確認（`/health`）、実際の文脈長の取得（`/props`）、ジョブの後や一定時間使わないときの終了、異常終了の検知と再起動、録音の開始で生成を止めたときにプロセスも終了してメモリを返す
- 思考を切る: 起動の引数で切る（Gemma 4。LM Studio では `reasoning_effort: "none"` で切っていた）。要求の側の指定も残す
- ログ: プロンプトと応答の本文をログに残さない（詳細仕様書 21 章）。llama-server の出力は、時刻・コード・所要時間・トークン数だけを拾う
- App: 設定画面（エンジンの選択、モデルの選択、接続の確認）、LLM-001 の案内文（「LM Studio が動いていない」→「推論エンジンを起動できない」）、初回の案内
- 評価: `Test-PhaseD.ps1` と `AudioProbe` を同梱のエンジンでも回せるようにし、LM Studio と同じモデル・同じ条件で比べる（精度・速さ・メモリ）
- 文書: 詳細仕様書・環境構築仕様書・`CLAUDE.md` の LM Studio の記述を書き換える（下の 5 章）

**含まない（後の段）**

- 更新の自動化（新しい版を見つける → 取ってくる → 評価セットで試す → 報告 → 利用者の承認で切り替え）。同梱のエンジンが動いてから、別の段で作る
- NFR-07 のための出力の抑制（下の 6 章。エンジンとは別の課題として並行して扱う）

## 4. 作業の順番（区切りごとにテストを通してコミットする）

| 段階 | 内容 | 確かめ方 |
|---|---|---|
| E1（済み 2026-11-05） | llama.cpp の版を決めて取得し、手で起動して確かめる: Radeon 890M（Vulkan）で動くか、`json_schema`、思考を切れるか、日本語、速さとメモリを LM Studio と比べる | 短い要求と評価セット 1 本。`environment-lock.md` に記録 |

| E3 | App: 設定（エンジン・モデル）、記録のジョブとの連携（ジョブの前に起動、後で終了、録音中は終了）、LLM-001 の案内 | ViewModel の単体テスト、実機の画面 |
| E4 | 評価: 同梱のエンジンで D5 の受入（調整用・受入用を 3 回ずつ、25 分の会議） | `Test-PhaseD.ps1` |
| E5 | 文書の書き換え | 差分を利用者が確認 |

- **D5 の受入（3 回ずつ・NFR-07）は、E4 で同梱のエンジンで測る**。LM Studio で測ってから置き換えると、速さとメモリを測り直すことになるため
- 記録を作る処理（区間の計画・検証・候補の検査）はエンジンと分けてあるので、変えない
- **E1 の結果**（`docs/environment-lock.md` 6 章「同梱の推論エンジン」）: b12121 の Vulkan 版で、E2B は毎秒 35 トークン・3.6 GB（LM Studio は 28〜30・4.6 GB）。**MTP（`--spec-type draft-mtp`、別ファイル）で毎秒 61 トークン・3.9 GB**。構造化出力・思考を切る・API キーを確かめた。MTP は既定で使う

## 6. 別に扱う課題: NFR-07（出力の量）

- Gemma 4 E2B は速い（毎秒 27〜30 トークン）が、25 分の会議で 1 区間に 4,000 トークン前後を書き、出力の上限 4,096 で 6 回切れて区間を半分にやり直した。4 区間で要求 17 回、**1,918 秒**（2026-11-05）
- 対策の候補: スキーマの件数の上限を下げる（章・文・候補）、1 区間の出力の目安をプロンプトに書く、区間を小さくする（出力の総量は減らないが、切れによるやり直しが減る）。評価セットで精度が落ちないことを確かめながら決める
- NFR-07 の基準（「Gemma 3 4B で 5 分以内」）そのものの見直しも、D5 の報告書で提案する

## 7. リスク

| リスク | 対策 |
|---|---|
| llama.cpp の配布形式が変わる（最新の v0.9.0 に Windows の配布物が見当たらない、2026-11-05） | E1 で、Windows の Vulkan 版がある版を選んで固定する。無ければ一つ前の版、またはビルドの手順を記録する |
| Radeon 890M の Vulkan で動きが違う | E1 で LM Studio と同じモデルの速さ・メモリ・出力を比べる |
| 異常終了でジョブが止まる | 終わった区間から再開する仕組み（D3）をそのまま使う。プロセスの再起動は 1 回まで |
| ほかのプロセスから使われる | ループバックのみ・起動ごとのランダムな API キー・ジョブの間だけ起動 |
| 版を上げる手間 | モデルを変えるときか不具合を直すときだけ上げ、そのたびに評価セットで確かめる（whisper.cpp と同じ運用）。自動化は後の段 |
